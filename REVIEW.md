# NetRunner Code Review

Scope: web_main.py, services/task_runner.py, services/host_service.py, services/menu_actions.py, computer/module/executor_ssh.py, computer/module/executor_scp.py, computer/module/local_executor.py, database/connection.py, database/orm.py, plus related web UI, scheduler, module registry, and repository code.

---

## Critical

### Security

1. **Command injection in remote SSH execution** — `computer/module/executor_ssh.py:7-8` builds `remote_cmd = f"sh -lc {shlex.quote(command)}"` and passes it as a single positional argument to `ssh`. The command itself is quoted, but it is executed inside `sh -lc`, so any caller that interpolates attacker-controlled values into `command` before calling `executor_ssh()` can inject shell metacharacters. Worse, `computer/users_module/ssh.py:35-44` (`mass_ssh.run`) and `computer/module/folder_swipe.py:6` interpolate user-provided strings directly into `command` or `dir` and run via shell with `subprocess.run(..., shell=True)`. This is a direct remote command-injection path through the web UI “Run module” form for `mass_ssh` and any module that reuses these helpers.
2. **Shell injection via `executor_scp`** — `computer/module/executor_scp.py:12-16` constructs `script = f"scp -P {port} ... {path_from} {path_to}"` and runs `subprocess.run(script, shell=True)` with no quoting. `path_from`/`path_to`/`port` are not validated, allowing trivial shell metacharacter injection.
3. **Shell injection in local executor** — `computer/module/local_executor.py:4-5` runs `subprocess.run(["sh", "-lc", f"{command}"], ...)`. The string is passed to `sh -lc`, and callers such as `computer/module/get_update.py:7-25` and `computer/module/termdraw.py` may run user-influenced commands. Any module or UI that can call `LocalComputer.local_executor` with unsanitized input is a local command-injection vector.
4. **Shell injection in hard drive / folder modules** — `computer/module/hard_drive_check.py:6` and `computer/module/folder_swipe.py:6-9` pass `host`/`port`/`dir` directly into an `ssh ...` command string and run with `shell=True`. `folder_swipe` also performs `sudo rm -rf {dir}` with unquoted input, compounding injection with destructive privileged operations.
5. **Hardcoded credentials / secrets** — `config_docker.py:1-5` contains `PASSPHRASE="123"`, `PASSWORD="password"`, and key paths. These defaults are used by multiple modules; they are committed and readable by anyone with access to the container filesystem. They are also referenced via `from config import *` everywhere.
6. **SSH host key verification disabled globally** — `computer/module/executor_ssh.py:15-17` sets `StrictHostKeyChecking=no` and `UserKnownHostsFile=/dev/null`. This makes all SSH connections vulnerable to MITM attacks. The same options are used in `webui/server.py:571-573` for `ssh-copy-id`. The `availability_check` module uses `ping`, not SSH, so the global disabling is unnecessary for it.
7. **Remote password exposure via `ssh-copy-id`** — `webui/server.py:537-589` runs `sshpass -p {password} ssh-copy-id ...` using a password typed by the operator. The password is passed as a command-line argument (visible in process lists, `/proc`, and container logs) and transmitted over SSH with host key verification disabled, exposing it to MITM and local snoopers. This also enables an attacker who can trigger `/api/hosts` to pivot credentials into the remote host.
8. **Weak SSH command-line construction with passphrases** — `computer/module/executor_ssh.py` does not support encrypted private keys; `config_docker.py` defines `PASSPHRASE` but it is never used. The key file is also read from a fixed, predictable location (`/app/keys/id_ed25519`) without per-host selection unless overridden, which is not a security issue itself but tied to the hardcoded default.
9. **Unrestricted dynamic module loading / code execution** — `webui/server.py:487-525` writes a user-uploaded base64-decoded Python file to `/app/modules/{file_name}` and immediately `exec_module`s it. There is no signature verification, sandboxing, or import restriction. The uploaded module can run arbitrary code at import time and is later executed via `TaskRunner`. This is a deliberate feature, but it is equivalent to arbitrary code execution on the NetRunner host and must be flagged as a critical security surface. The API also trusts `module_path` from the client (`webui/server.py:499-502`), allowing path traversal in the file name.
10. **Arbitrary file read via report serving** — `webui/server.py:448-452` resolves `Path(self.ctx.reports_dir) / report_path` and checks `str(target.resolve()).startswith(str(Path(self.ctx.reports_dir).resolve()))`. On POSIX, `startswith` path comparison can be bypassed by case-sensitivity or symlink tricks in some environments, though the current implementation is mostly correct. More importantly, `webui/server.py:455-458` uses `str(target).startswith(str(STATIC_DIR.resolve()))` without calling `.resolve()` on `target`, so a path such as `/static/..%2f..%2fetc/passwd` may bypass the guard on the non-normalized string while `target` still resolves to a file outside the static directory.
11. **No authentication / authorization on the web API** — `webui/server.py` exposes all endpoints without any login, session, token, or role checks. Anyone who can reach the server can add hosts, run modules, upload and execute Python modules, delete the database, read reports, and trigger `ssh-copy-id` with arbitrary credentials. This is inconsistent with the README’s framing as a “deployment package” but is not mentioned as a security limitation.
12. **Path traversal in uploaded SSH key names** — `webui/server.py:599-602` uses `Path(name).name` but the key is later placed under `keys_dir / base_name`; an attacker who provides a crafted name like `../../tmp/id_ed25519` could write the key outside the intended directory if `.name` does not strip directory components. `Path("../../tmp/key").name` does return `key`, so the specific implementation is safe, but the API does not validate the name and stores the raw path in the database.
13. **SQL injection in repository ordering** — `database/repos/base.py:31` and `:46` interpolate `order_by` directly into the SQL string: `f'SELECT * FROM {self.table_name} ORDER BY {order_by}'`. The table name is also interpolated. While callers currently pass hardcoded values, any user-controlled `order_by` (e.g., from a query parameter) would be a direct SQL injection vector. The pattern is repeated across repositories and should be parameterized/whitelisted.
14. **Database writes are not protected from concurrent access** — SQLite is opened in `database/connection.py:10` with default options and WAL mode, but all database operations use the same `sqlite3.Connection` from a single thread. The web server (`HTTPServer`) is single-threaded, but the scheduler tick and the periodic ping thread (`webui/server.py:646-661`) open independent `Database` objects, which is good. However, `BaseRepository.update()`/`create()` call `self.conn.commit()` per operation, and there is no retry on `SQLITE_BUSY`; concurrent CLI and web usage could raise `OperationalError`.
15. **Scheduler does not mark tasks as failed on exception** — `services/scheduler.py:10-23` calls `task_runner.run_template()` and only calls `mark_ran()` on success. If the task fails, the exception is logged but the scheduled task is never marked as failed or disabled, so a recurring task will be re-due immediately and retry repeatedly until manually disabled, because `mark_ran()` disables `is_enabled`. This is actually a one-shot scheduler, which may not match the README “scheduler” expectation.

### Correctness / Data Loss

16. **One-shot scheduler disables tasks permanently** — `services/scheduler.py:21` and `database/repos/schedule_repo.py:27-32` set `is_enabled=0` after the first run. The README describes “scheduled tasks” and the web UI has a checkbox for “Активна”, but the system never re-runs a recurring task. This is either a major bug or a naming mismatch.
17. **Availability check uses the wrong command for host reachability** — `services/host_service.py:75-91` checks a host by running `computer.executor_ssh("echo netrunner-ok")`, but `computer/module/availability_check.py` uses `ping`. The `check_host` result parsing is brittle (`"[ERROR]" not in result and ... "netrunner-ok" in result`), so any partial SSH output that contains `netrunner-ok` is treated as success, even if the exit code was non-zero. This does not match the module’s intended behavior and can produce false positives.
18. **`TaskRunner` marks a run as success even if the module reports errors in its dictionary** — `services/task_runner.py:76-83` only writes `status="success"` based on the absence of a Python exception. A module can return `{"status": "error"}` and still be recorded as success because the runner never inspects module-specific status fields.
19. **`TaskRunner.run` does not record partial failures for groups** — `services/task_runner.py:46-83` calls `registry_item.instance.run(...)` once for the entire target list. If the module returns a dict, per-host results are stored; if it returns a string, the same string is recorded for every host. The runner does not verify that the per-host list length matches the target count, so group-run results can be misleading or silently truncated.
20. **`mass_ssh` does not quote the user command passed into `executor_ssh`** — `computer/users_module/ssh.py:35-44` takes a web-supplied `command` and passes it to `Computer.executor_ssh(command)`. `executor_ssh` does `shlex.quote(command)` once, so the outer argument is safe from the SSH command line, but the command is then run as `sh -lc 'command'` on the remote host. Because the command itself is not validated, any command string that the operator typed can be malicious; however, the real issue is that `mass_ssh` can be used to run arbitrary commands on all registered hosts with no additional authorization, which is expected for an automation tool but must be explicitly gated by access control (see C11).
21. **Inventory collection never records `raw_json` or `package_count`** — `computer/module/inventory_collect.py:148-161` sets `raw_json=""` and `package_count=None`, so the schema fields are never populated. The README says the tool collects “system information”, but the collected raw data is discarded.
22. **Inventory collection uses host address instead of `inventory_items` host_id** — `computer/module/inventory_collect.py:176-191` builds `per_host_results` using `host.address`/`host.port` from the loop variable, which is correct, but the inner list comprehension uses `summary_lines[i].split(" | ")[0]` for the name and `item["host_id"]` for the ID. If a host fails, the inventory item is still created but its fields are empty, and the index mapping remains aligned only because both lists are appended in the same loop order; any future early `continue` would break the alignment.
23. **Group host membership may be silently lost on host update** — `webui/server.py:223-231` only updates the group link if `new_group_id` is provided in the payload. If the UI omits the field, the existing link is preserved, which is correct, but if `new_group_id` is `0`, it is treated as a valid group because `if new_group_id:` is false only for `None`/empty, not `0`. This is a subtle bug because a group with id `0` cannot exist in SQLite, but the check is still wrong.
24. **Default values for `run_at` in scheduled tasks are empty strings** — `webui/server.py:360` and `app.js:978-979` may pass an empty `run_at` to `db.scheduled.create()`. `ScheduledTaskRepo.create()` does not validate it, so the row is inserted with an empty string and will never be selected by `due()` (which compares `run_at <= ?`), silently disappearing from the scheduler.
25. **`TaskRunner.run_template` ignores `target_type`/`target_id` validation** — `services/task_runner.py:96-112` passes the caller-provided target values straight to `run`. If the target does not exist, the run is created with status `running`, then fails and is recorded as `error`. This is acceptable but wasteful; the bigger issue is that the scheduler stores the same target values and runs them with no existence check before run-time.
26. **`TaskRunner` does not check if a module is enabled before running it** — `services/task_runner.py:23-27` checks only that the module row exists. A disabled module (`is_enabled=0`) can still be executed via `/api/run` or scheduled tasks because the runtime registry holds the instance and the database flag is never consulted.
27. **Report service uses table-name interpolation and table-name-agnostic CSV** — `services/report_service.py` calls `self.db.task_runs.all()`, which is vulnerable to C13 above. Also, `_write_csv` uses `items[0].keys()` as fieldnames; if the first row is a dataclass whose keys are not always consistent (e.g., `None` rows), an empty CSV could be written with no headers. This is minor but affects report correctness.
28. **Missing error handling for `subprocess.run` in `executor_ssh`** — `computer/module/executor_ssh.py:25-30` does not pass `check=True` or `timeout`. A hanging SSH call will block the web server indefinitely (see also C33). The `ConnectTimeout=5` option helps but is not a hard process timeout.
29. **No validation that the SSH key actually exists** — `computer/module/executor_ssh.py:9` builds `Path(KEY_PATH) / KEY_NAME` and passes it to `ssh -i`. If the key is missing, `ssh` fails. More importantly, `host_service.to_computer()` does not pass `ssh_key_id`, so every host uses the same hardcoded key from `config.py` regardless of the database value. The README says the UI allows selecting an SSH key, but that selection is ignored for actual SSH execution.
30. **Host key provisioning ignores the actual selected key file** — `webui/server.py:546-549` resolves the key by `ssh_key_id` or default, but the remote SSH modules (C29) never use this resolved key. The provisioning path and the execution path are therefore disconnected; a host record may be associated with a key that is never used for execution.
31. **Docker startup uses hardcoded `id_ed25519` and password defaults** — `startup.sh:14-16` generates an unencrypted key and `init_demo.py:24-25` hardcodes the same path. The README describes the default password as `admin` for test hosts, but `config_docker.py` sets `PASSWORD="password"`. The mismatch means the demo may not authenticate unless the Alpine host setup script uses `admin`.
32. **`init_demo.py` creates module records that do not match the registry** — lines 78-91 register `availability_check`, `inventory_collect`, `mass_ssh` with paths `computer.module.*`, but `computer/module/__init__.py` dynamically imports the same classes and registers them with `Modules.add_update()`. The class names `AvailabilityCheck`, `SSHExecutor` do not exist in the source files (the actual classes are `UserModule`). The record is used by `TaskRunner` only for the slug, but the schema field `class_name` is misleading and could break future reflection.
33. **Web server is single-threaded and synchronous** — `webui/server.py:626-666` uses `http.server.HTTPServer` with a synchronous request handler. Any long-running SSH command (e.g., `mass_ssh` with a slow command, inventory collection, or report export) blocks all other web requests and the periodic ping thread does not help because it opens its own DB. This is a major architectural limitation for a remote-host automation tool and should be noted in the README or fixed.

## Major

### Security

34. **`subprocess.os.environ` usage is non-standard and brittle** — `webui/server.py:556-560` writes `env = {**subprocess.os.environ, ...}`. `subprocess.os` is just `os` imported via the `subprocess` module, but relying on that alias is fragile and unclear; it should be `os.environ`.
35. **Passwords are stored in the host record only transitively** — `webui/server.py:184` extracts `password` from the add-host payload and passes it to `ssh-copy-id`, but the password is never stored in the database. This is correct behavior, but there is no audit log of the provisioning attempt, and failures are returned to the client with full stderr, possibly leaking host information.
36. **SSH key upload accepts any file type** — `webui/server.py:423-440` only checks that `name` and `file_data` are present; it does not validate that the decoded content is a valid private key. Malformed keys can be uploaded and later passed to `ssh -i`, causing confusing failures. The UI `accept="*/*"` also allows arbitrary files.
37. **No rate limiting or input validation on the web API** — Any client can flood `/api/run`, `/api/hosts`, `/api/modules`, `/api/task-runs/clear`, etc. There is no request size limit, no CORS policy, and no origin check. The `Content-Length` header is trusted in `_read_json_body` without an upper bound.
38. **Base64-decoded module files are written without a size limit** — `webui/server.py:504` decodes `file_data` and writes it directly. A large upload can exhaust disk space or memory.
39. **Uploaded module files can overwrite each other** — `webui/server.py:599-610` deduplicates by counter for the same stem, but the slug lookup in `ModuleRegistry` is by `slug`. A user can upload a file named `evil.py` with a slug `availability_check`, and the registry lookup will return the previously registered `availability_check` instance unless the new module is re-registered. This is a confused-deputy / module substitution risk.
40. **SQL `clear_all` resets the sequence but does not vacuum** — `database/repos/task_run_repo.py:52-55` and the analogous report clear are fine for functionality, but the API `/api/task-runs/clear` and `/api/reports/clear` allow any unauthenticated user to wipe audit history (see C11).
41. **No integrity check on `per_host_json` / `args_json` before deserialization** — `services/task_runner.py:103` uses `json.loads(template.default_args_json)`; `services/report_service.py:327-328` uses `json.loads(task_run.per_host_json)` with broad exception suppression. While JSON is safer than pickle, arbitrary untrusted JSON can still cause resource exhaustion (deeply nested objects) because there is no depth limit. The `args_json` passed to modules is also attacker-controlled if the module accepts user args via the web API.
42. **The `config.py` module is imported with `from config import *`** — Several modules use `from config import *`, which pollutes namespaces and makes static analysis hard. It also means any name added to `config.py` can accidentally shadow local variables. More importantly, `config.py` is not in the provided file list; the codebase appears to rely on `config_docker.py` being renamed to `config.py` in the Docker image. If run outside Docker, imports will fail unless an operator creates `config.py` manually.
43. **The `mass_ssh` module prompt is interactive-only** — `computer/users_module/ssh.py:28-32` calls `input()` inside `prompt_args()`. This works in the TUI but will block or fail in a web/non-interactive context because the web runner does not implement `prompt_args`. The UI manually adds the `command` arg for `mass_ssh` (app.js:994-996), but this special-casing is brittle; any other module with `prompt_args` is unusable via the web.
44. **No sandboxing of user modules** — `services/app_context.py:139-168` dynamically loads every `.py` file in `/app/modules` and registers it. The imported modules run their top-level code immediately, so any `__init__` side effects, network calls, or malicious logic execute at startup. There is no isolation, no whitelist of imports, and no audit of the loaded code.

### Correctness / Architecture

45. **`Computer` class mixes unrelated responsibilities** — `computer/__init__.py:7-33` bundles SSH, SCP, hard-drive check, ping, and folder swipe into one class. It also writes to `./blacklist_program` inside `folder_swipe`, which is a local file side effect in a method meant to operate on a remote host. The `dir` parameter is not validated, and `blacklist_program` is never read or used elsewhere.
46. **`Computer.ping()` parses the host string incorrectly** — `computer/__init__.py:26` does `ip=self.host.split("@")[1]`. If the host string does not contain `@`, it raises `IndexError`. The `ping` module itself does not use SSH credentials, so this is a fragile coupling.
47. **`HostService.to_computer()` ignores the database SSH key** — `services/host_service.py:66-70` creates a `Computer` with only `host` and `port`. It does not pass the key path, so the host’s `ssh_key_id` is effectively dead data. This contradicts the UI and the README, which describe per-host key selection.
48. **`HostService.check_host()` swallows all exceptions in `check_all_hosts()`** — `services/host_service.py:93-103` catches `Exception` and does nothing, so a host that causes an exception (e.g., invalid SSH key) is counted as inactive but no error is logged or returned. This hides configuration problems.
49. **`TaskRunner` does not respect module `is_enabled`** — As noted in C26, the database flag is ignored. A disabled module should be rejected at runtime.
50. **`TaskRunner` does not support retries or timeouts** — A slow SSH command blocks the runner (and the web server) indefinitely. There is no timeout in `executor_ssh`, no worker pool, and no cancellation mechanism.
51. **`TaskRunner.run` is not re-entrant / thread-safe** — The runner uses the shared `self.db` connection. If the scheduler tick and the web server both call `run()` concurrently, SQLite errors can occur. The current web server is single-threaded, but the scheduler tick is called from `/api/scheduler/tick` and from the startup ping thread, creating a real concurrency risk.
52. **`Scheduler.tick()` runs all due tasks sequentially and synchronously** — `services/scheduler.py:10-23` loops through due tasks and runs each one in the same thread. If there are many tasks or slow targets, later tasks are delayed. This is not a scheduler but a sequential batch runner.
53. **`Scheduler` does not reschedule or mark failures** — One-shot disabling (C16) means there is no concept of a recurring task. The README mentions “scheduler” but does not clarify this limitation.
54. **`ScheduledTaskRepo.due()` uses ISO string comparison** — `database/repos/schedule_repo.py:15-25` compares `run_at <= ?` as TEXT. ISO 8601 strings with consistent offset formatting sort correctly, but mixed offset formats (`+00:00` vs `Z` vs local offsets) can produce wrong ordering. The UI converts to local ISO (app.js:705-727), which may include offsets like `+03:00`, but the database does not normalize them.
55. **`ScheduledTaskRepo.mark_ran()` always disables the task** — `database/repos/schedule_repo.py:27-32` sets `is_enabled=0`. This is the root cause of C16 and C53.
56. **`TaskRunRepo.clear_all()` is not parameterized by repository** — Every repository that needs bulk clearing would have to duplicate the SQL. This is a DRY concern, but the bigger issue is the lack of authorization (C40).
57. **`BaseRepository.all(order_by=...)` allows SQL injection by design** — C13. This should be fixed with a whitelist.
58. **`BaseRepository.filter()` does not support ranges, LIKE, or sorting** — The repository layer is very basic; for example, there is no way to search hosts by name or address efficiently. This is fine for a small app but limits future reporting.
59. **`model_to_dict` in `webui/server.py` and `services/report_service.py` duplicates serialization logic** — Both files define a helper to convert dataclasses/rows to dicts. The duplication is minor but could be centralized.
60. **`webui/server.py` imports `open_database` and `HostService` directly** — It also uses `self.ctx.host_service` for most operations, but the direct import and manual DB open in `_periodic_ping` create inconsistent paths. If the app context changes the database connection logic, the ping thread will not follow it.
61. **`_periodic_ping` opens a new database connection per tick** — `webui/server.py:647-655` opens and closes the database every 60 seconds. This is inefficient and can miss in-flight updates if the main connection holds a long transaction. It also uses the same `db_path`, so it works, but it is not integrated with the app context’s lifecycle.
62. **`webui/server.py` returns full tracebacks to the client** — `do_GET` and `do_POST` catch all exceptions and return `traceback.format_exc()` in the JSON error body. This leaks file paths, source code, and internal details to any unauthenticated client (C11).
63. **The web UI does not show the inventory view** — `index.html` defines `section id="view-inventory"`, but the navigation sidebar does not have a button for it; the only way to view inventory is through the dashboard cards or the API. This is a UI/UX bug.
64. **The web UI inventory view exists but is unreachable from the menu** — Related to C63: the app.js `viewMeta` includes `inventory`, but there is no sidebar link, so users cannot navigate there by clicking.
65. **`app.js` uses `innerHTML` with HTML from the server in some places** — Most dynamic HTML is generated from local state, but the task result output is inserted as `textContent` (good). However, the report list and module tables use `innerHTML` with `escapeHtml`, which is generally safe, but the `playModule` function uses `onclick="playModule('${escapeHtml(r.slug)}')"` — `escapeHtml` does not escape backticks or `${}` inside HTML attributes, which could matter if a slug contains backticks (slugs are controlled by the server, so this is low risk but still non-idiomatic; better to use event listeners).
66. **`app.js` `viewReport` passes the file path through the URL** — `viewReport` does `fetch(`/reports/${encodeURIComponent(fileName)}`)`. The server path check uses `report_path = path[len("/reports/"):]` which, combined with URL decoding by `urlparse`, should be safe, but the URL encoding is the only guard. A `%2f` in the file name is decoded to `/` before the path check, which is a known edge case in many Python path traversal checks. The current `startswith` check on resolved paths is the saving factor.
67. **`index.html` has a commented-out brand element but still ships it** — Minor HTML hygiene.
68. **`module_registry.py` registers the same instance under multiple slugs if called twice** — `_items[slug] = record` overwrites, but the database is updated by `id`. If `slug` is reused, the DB row may be updated to a different `module_path`/`class_name`, causing confusion between the registry and the DB.
69. **`module_registry.py` `_slugify` allows Cyrillic and hyphens in slugs** — `[^a-zA-Z0-9_а-яА-Я-]` means slugs can contain Cyrillic and hyphens. This is a design choice, but it can cause issues with file system paths, URL parameters, and database indexes. The web UI uses slugs in URLs and `escapeHtml`, which should handle UTF-8, but the filesystem module filename uses the slug only if `file_name` is empty, which may create non-ASCII file names.
70. **`module_registry.py` `register_menu_items` ignores the `name` key of the dict** — It calls `register_instance(instance=instance, is_builtin=is_builtin)` without passing `name`, so the title defaults to `getattr(instance, "title", class_name)`. The `title` attribute may be set in `__init__`, which is fine because `register_instance` is called after the instance is created, but the original `name` from the menu dict is silently discarded. This is inconsistent with the data structure.
71. **`computer/module/__init__.py` and `computer/users_module/__init__.py` use a global mutable `_Modules` / `_UserModules` object** — This is a code smell: global state makes testing hard and can lead to duplicate registration if the module is imported more than once. The import side effects also register modules at import time, which is the cause of C44.
72. **`computer/module/__init__.py` does not import `mass_ssh` from the registry path** — `init_demo.py` records `mass_ssh` as `computer.module.executor_ssh` with class `SSHExecutor`, but `computer/module/__init__.py` imports `executor_ssh` as a function, not a class. The actual `mass_ssh` module lives in `computer/users_module/ssh.py`. This mismatch between the registry and the filesystem is confusing and fragile.
73. **`computer/module/folder_swipe.py` hardcodes user `rmk:rmk`** — The chown command uses `rmk:rmk`, which is a specific local account. This will not work on generic Alpine hosts and may cause permission errors. The README does not mention this account.
74. **`computer/module/installer.py` hardcodes package `blender` and Debian-based `apt-get`** — The package is hardcoded to `blender`, and the command uses `apt-get`, which is not available on Alpine. This module is not registered in the demo but still exists in the source and is a poor example.
75. **`computer/module/installer.py` embeds the password in the remote command** — `echo {PASSWORD} | sudo -S apt-get install ...` exposes the password in the remote shell history and process list. This is a bad pattern even if the password is not used elsewhere.
76. **`computer/module/hard_drive_check.py` uses relative path `./{KEY_PATH}`** — `KEY_PATH` from config is `/app/keys`, so `./{KEY_PATH}` expands to `./app/keys`, which is wrong. The function would not find the key unless the working directory is `/`.
77. **`computer/module/executor_scp.py` constructs a `scp` command but never returns the result** — The function returns the `subprocess.CompletedProcess` object or an error string, but callers must inspect it. The return type is inconsistent.
78. **`computer/module/local_executor.py` does not handle non-zero exit codes** — It returns only stdout, so failures are silently ignored. The commented-out `check=True` and `errors="replace"` indicate unfinished code.

The actual output of `ping -c 1 -q` on Linux is `1 packets received`, but this is locale-dependent and brittle. The exit code is more reliable (the `ping` module already returns it via `check=True`).

The name “availability_check” is misleading compared to `host_service.check_host()`, which does SSH. The README calls it “Проверка доступности”, which is vague, but for an automation tool, ping-only availability is insufficient.

It also does not validate types, so an integer stored as text will cause runtime errors in downstream code.

85. **`database/orm.py` `import_legacy_hosts_json()` does not validate IP/address format** — It splits on `@` and creates a host with the raw string. A malformed entry like `user@` or `@host` will produce empty address or username. It also silently skips non-string entries instead of reporting them.

The web UI does not use this path, but the TUI does.

The web UI uses `datetime-local` and converts to ISO 8601 with offset, which the CLI parser does not accept. This means scheduled tasks created via the web UI will parse through the second branch (`strptime`) and fail because the string includes an offset. This is a real bug: the web sends `2026-06-15T12:00:00+03:00`, but `_parse_run_at` only accepts `2026-06-15 12:00`. The TUI will say it cannot parse the time. The web path does not call `_parse_run_at`, so it works by accident, but the TUI path is broken.

This is a serious name-conflict risk.
93. **`services/app_context.py` `_load_user_modules_from_disk()` does not sanitize the slug before using it as a module name** — A slug with spaces or special characters could cause an invalid module name or import error. `_slugify` is only used in `register_instance`, not before loading from disk.

If a task is slow or a host is unreachable, startup is delayed. It also runs on the main thread, blocking startup.

## Summary of highest-priority fixes

1. Add authentication/authorization to the web API (or clearly document its absence and restrict network access).
2. Stop disabling SSH host key verification; allow operators to manage a known_hosts file or accept the risk explicitly per-host.
3. Replace all `subprocess.run(..., shell=True)` with list-based commands and strict quoting/validation; never pass unsanitized user input to the shell.
4. Validate and sanitize `command`/`dir` arguments in modules, especially `mass_ssh`, `folder_swipe`, `executor_scp`, and `local_executor`.
5. Remove hardcoded credentials from `config_docker.py` and the README; generate or require configuration at runtime.
6. Make the scheduler support recurring tasks and proper failure marking, or rename it and document that it is one-shot.
7. Fix the web/TUI time-format mismatch for scheduled tasks so the TUI can parse web-created schedules.
